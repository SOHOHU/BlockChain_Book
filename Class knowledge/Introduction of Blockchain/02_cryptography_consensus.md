# 密码学与共识机制

## 1、密码学基础

密码学是区块链安全的基石。如果没有密码学，区块链就无法保证数据的安全性和不可篡改性。在这一章节中，我们将深入了解区块链中使用的核心密码学技术。

---

### 1.1、密码学的目标

在区块链系统中，密码学主要实现以下四个目标：

| 目标 | 说明 | 在区块链中的应用 |
|------|------|----------------|
| **机密性** | 确保信息只能被授权者访问 | 私钥保护、交易隐私 |
| **完整性** | 确保信息未被篡改 | 区块哈希、交易验证 |
| **认证性** | 验证信息发送者的身份 | 数字签名、地址验证 |
| **不可否认性** | 防止发送者否认已发送的信息 | 交易签名、智能合约执行记录 |

---

### 1.2、哈希函数详解

#### 1.2.1、什么是哈希函数？

哈希函数是一种将任意长度的输入数据映射为固定长度输出的数学函数。你可以把它想象成一个"数据指纹生成器"——无论输入多长，输出总是固定长度。

**数学表示:**
```
H: {0,1}* → {0,1}^n
```
其中n是固定的输出长度（比如SHA-256输出256位）。

**简单例子:**
```
输入: "Hello, World!"
输出 (SHA-256): dffd6021bb2bd5b0af676290809ec3a53191dd81c7f70a4b28688a362182986f

输入: "Hello, World?" (仅改变一个字符)
输出 (SHA-256): c0535e4be2b79ffd93291305436bf889314e4a3faec05ecffcbb7df31ad9e51a
```

注意：即使只改变一个字符，输出完全不同！这就是哈希函数的"雪崩效应"。

#### 1.2.2、密码学哈希函数的特性

一个合格的密码学哈希函数必须满足以下特性：

**1. 确定性 (Deterministic)**
- 相同的输入总是产生相同的输出
- 这使得验证变得可能

**2. 快速计算 (Fast Computation)**
- 可以在合理时间内计算出哈希值
- 但也不能太快，否则无法抵御暴力破解

**3. 单向性 (One-way/Pre-image Resistance)**
- 从输出难以推导出输入
- 即：已知 H(x)，难以找到 x

**数学表述:**
```
给定哈希值 h = H(x)
找到 x 使得 H(x) = h 在计算上是不可行的
```

**4. 雪崩效应 (Avalanche Effect)**
- 输入的微小变化导致输出的巨大变化
- 改变一个bit，平均有50%的输出bit会改变

**5. 抗碰撞性 (Collision Resistance)**

碰撞是指两个不同的输入产生相同的输出。抗碰撞性有两个层次：

**弱抗碰撞性 (Second Pre-image Resistance):**
```
给定 x1，难以找到 x2 ≠ x1 使得 H(x1) = H(x2)
```

**强抗碰撞性 (Collision Resistance):**
```
难以找到任意 x1 ≠ x2 使得 H(x1) = H(x2)
```

#### 1.2.3、SHA-256算法详解

SHA-256（Secure Hash Algorithm 256-bit）是比特币和许多区块链系统使用的哈希算法。

**基本信息:**
- 输出长度：256位（32字节）
- 设计者：美国国家安全局(NSA)
- 发布时间：2001年

**SHA-256的工作流程:**

```
输入消息 → 消息填充 → 消息分块 → 迭代压缩 → 输出哈希值
```

**详细步骤:**

**步骤1：消息填充 (Padding)**

目标是让消息长度 ≡ 448 (mod 512)

1. 在消息末尾添加一个"1"
2. 添加k个"0"，使得消息长度 = 448 mod 512
3. 添加64位的原始消息长度

**示例:**
```
原始消息: "abc" (24位)
填充后:   "abc" + 1 + 423个0 + 24的64位表示
总长度:   512位 (一个完整的块)
```

**步骤2：初始化哈希值**

SHA-256使用8个32位的初始哈希值：
```
h0 = 0x6a09e667
h1 = 0xbb67ae85
h2 = 0x3c6ef372
h3 = 0xa54ff53a
h4 = 0x510e527f
h5 = 0x9b05688c
h6 = 0x1f83d9ab
h7 = 0x5be0cd19
```

这些值是前8个质数平方根的小数部分。

**步骤3：处理每个512位的消息块**

对每个512位块执行64轮压缩运算：

```
For i = 0 to 63:
    1. 准备消息调度 (Message Schedule)
    2. 执行压缩函数
    3. 更新工作变量
```

每轮使用不同的常数 K[i]（前64个质数立方根的小数部分）。

**步骤4：输出最终哈希值**

将8个32位的值拼接成256位的最终哈希值。

#### 1.2.4、哈希函数在区块链中的应用

**1. 区块链接 (Block Chaining)**

每个区块包含前一个区块的哈希值：
```
Block N:
  Previous Hash: H(Block N-1)
  Transactions: [Tx1, Tx2, ...]
  Nonce: 12345
  
Block Hash = H(Previous Hash + Transactions + Nonce + ...)
```

**2. Merkle树 (前面已经讨论过)**

**3. 工作量证明 (Proof of Work)**

找到一个nonce使得：
```
H(Block Header) < Target
```

**4. 地址生成**

比特币地址生成过程：
```
私钥 → 公钥 → SHA256 → RIPEMD160 → 添加版本 → Base58编码 → 地址
```

### 1.3、数字签名技术

数字签名是区块链中验证交易真实性的核心技术。它解决了一个关键问题：**如何在不泄露私钥的情况下，证明我拥有某个账户？**

#### 1.3.1、数字签名的工作原理

数字签名基于**非对称加密**，使用一对密钥：
- **私钥 (Private Key)**：保密，用于签名
- **公钥 (Public Key)**：公开，用于验证签名

**签名过程:**
```
1. 发送者用私钥对消息进行签名
   Signature = Sign(Message, Private_Key)

2. 任何人都可以用公钥验证签名
   Valid = Verify(Message, Signature, Public_Key)
```

**关键性质:**
- 用私钥签名的消息，只能用对应的公钥验证
- 无法从公钥推导出私钥
- 签名与消息绑定，无法将签名用于其他消息

#### 1.3.2、ECDSA (椭圆曲线数字签名算法)

比特币和以太坊使用的是ECDSA，它基于椭圆曲线密码学。

**为什么使用ECDSA而不是RSA？**

| 特性 | RSA | ECDSA |
|------|-----|-------|
| **密钥长度** | 2048-4096位 | 256位 |
| **安全级别相同时** | 密钥更长 | 密钥更短 |
| **计算速度** | 较慢 | 较快 |
| **适合区块链** | 否 | 是 |

**椭圆曲线基础:**

椭圆曲线的标准方程：
```
y² = x³ + ax + b (mod p)
```

比特币使用的曲线是 **secp256k1**:
```
y² = x³ + 7 (mod p)
其中 p = 2²⁵⁶ - 2³² - 2⁹ - 2⁸ - 2⁷ - 2⁶ - 2⁴ - 1
```

**ECDSA密钥生成:**

```
1. 选择私钥 d (一个256位的随机数)
   范围: 1 ≤ d ≤ n-1 (n是曲线的阶)

2. 计算公钥 Q = d × G
   其中 G 是曲线的基点
   × 表示椭圆曲线上的点乘运算
```

**ECDSA签名过程:**

```
输入: 消息 m, 私钥 d

1. 计算消息哈希
   e = H(m)

2. 选择随机数 k (每次签名都要不同!)
   1 ≤ k ≤ n-1

3. 计算点 P = k × G = (x, y)

4. 计算 r = x mod n
   如果 r = 0，回到步骤2

5. 计算 s = k⁻¹(e + rd) mod n
   如果 s = 0，回到步骤2

6. 签名为 (r, s)
```

**ECDSA验证过程:**

```
输入: 消息 m, 签名 (r, s), 公钥 Q

1. 计算消息哈希
   e = H(m)

2. 计算
   u1 = s⁻¹ × e mod n
   u2 = s⁻¹ × r mod n

3. 计算点 P = u1 × G + u2 × Q = (x, y)

4. 验证 r ≡ x (mod n)
   如果相等，签名有效
```

**为什么这个验证过程有效？**

数学证明（简化版）：
```
P = u1 × G + u2 × Q
  = (s⁻¹e) × G + (s⁻¹r) × Q
  = (s⁻¹e) × G + (s⁻¹r) × (d × G)
  = s⁻¹(e + rd) × G
  = s⁻¹ × s × k × G    (因为 s = k⁻¹(e + rd))
  = k × G
  = 原始签名时的点P

因此 x坐标相同，r也就相同
```

#### 1.3.3、数字签名在区块链中的应用

**1. 交易授权**

在比特币中，花费UTXO需要提供数字签名：
```
交易输入 = {
  前一个交易哈希,
  输出索引,
  签名脚本 (包含签名和公钥)
}
```

验证过程：
1. 从签名脚本中提取公钥
2. 从公钥生成地址
3. 验证地址与UTXO的锁定地址匹配
4. 验证签名的有效性

**2. 防止交易篡改**

签名与交易内容绑定，任何修改都会导致签名失效：
```
原交易: A → B (10 BTC)
签名: Sign(原交易, A的私钥)

如果有人修改为: A → C (10 BTC)
原签名将无法通过验证
```

**3. 身份认证**

公钥哈希后得到的地址代表身份：
```
私钥 → 公钥 → 地址

只有拥有私钥的人才能：
- 签署该地址的交易
- 证明对该地址的控制权
```

## 2、共识机制

共识机制是区块链的心脏。在一个去中心化的网络中，如何让成千上万个互不信任的节点对网络状态达成一致？这就是共识机制要解决的问题。

---

### 2.1、拜占庭将军问题

在深入了解各种共识机制之前，我们需要先理解一个经典的计算机科学问题：**拜占庭将军问题**。

#### 2.1.1、问题描述

想象这样一个场景：

```
拜占庭帝国的军队围攻一座敌城
多位将军指挥不同的军队部分
将军们只能通过信使通信
目标：所有将军必须就"进攻"或"撤退"达成一致

挑战：
1. 信使可能被敌人截获或延迟
2. 部分将军可能是叛徒（拜占庭节点）
3. 叛徒会发送错误或矛盾的信息
4. 忠诚的将军必须达成一致的决策
```

**为什么这个问题重要？**

在区块链中：
- 将军 = 网络节点
- 信使 = 网络通信
- 叛徒 = 恶意节点或故障节点
- 决策 = 对区块链状态的共识

#### 2.1.2、拜占庭容错的理论边界

经典的拜占庭将军问题研究表明：

**理论结论:**
```
对于 n 个节点，其中有 f 个拜占庭节点
要达成共识，必须满足: n ≥ 3f + 1

换句话说：
- 至少需要 67% 的诚实节点
- 最多只能容忍 33% 的拜占庭节点
```

**实例:**
| 总节点数 (n) | 最多容忍拜占庭节点 (f) | 诚实节点要求 |
|-------------|---------------------|------------|
| 4 | 1 | 至少3个 |
| 7 | 2 | 至少5个 |
| 10 | 3 | 至少7个 |
| 100 | 33 | 至少67个 |

**消息复杂度:**

传统拜占庭容错算法（如PBFT）的消息复杂度是 O(n²)，这意味着在大规模网络中会产生海量通信。

---

### 2.2、工作量证明 (Proof of Work, PoW)

PoW是比特币使用的共识机制，也是第一个成功解决拜占庭将军问题的实用方案。

#### 2.2.1、PoW的核心思想

**基本原理:**

要获得记账权（生成新区块），节点必须完成一个计算难题：

```
找到一个 nonce，使得:
H(BlockHeader + nonce) < Target

其中:
- H 是哈希函数 (SHA-256)
- Target 是难度目标值
- nonce 是要找的随机数
```

**为什么这能达成共识？**

1. **计算困难，验证容易**
   - 找到nonce需要大量计算（平均需要尝试2^n次）
   - 验证只需要一次哈希计算

2. **概率公平**
   - 算力越大，找到nonce的概率越高
   - 但不能保证一定找到

3. **经济激励**
   - 找到有效区块获得奖励（区块奖励 + 交易费）
   - 作恶会浪费算力资源

#### 2.2.2、PoW挖矿详细流程

**完整的挖矿过程:**

```
1. 收集交易
   - 从内存池收集待确认交易
   - 验证每笔交易的有效性
   - 按交易费排序，优先打包高手续费交易

2. 构造Coinbase交易
   - 创建特殊交易，接收者是矿工自己
   - 金额 = 区块奖励 + 所有交易费

3. 构建Merkle树
   - 将所有交易（包括Coinbase）构建成Merkle树
   - 计算Merkle根

4. 构造区块头
   区块头包含:
   - 版本号
   - 前一个区块哈希
   - Merkle根
   - 时间戳
   - 难度目标 (nBits)
   - Nonce (初始为0)

5. 开始挖矿
   While True:
       hash = SHA256(SHA256(BlockHeader))
       
       if hash < Target:
           # 找到了! 广播区块
           broadcast(Block)
           break
       else:
           nonce += 1
           if nonce > 2^32:
               # nonce溢出，修改其他字段（如时间戳或Coinbase）
               更新区块头
               nonce = 0

6. 等待网络确认
   - 其他节点验证区块
   - 如果有效，添加到本地区块链
   - 矿工获得奖励
```

#### 2.2.3、难度调整机制

比特币的目标是平均每10分钟产生一个区块。为了实现这个目标，网络会动态调整挖矿难度。

**难度调整公式:**

```
新难度 = 旧难度 × (实际时间 / 期望时间)

其中:
- 每2016个区块调整一次
- 期望时间 = 2016 × 10分钟 = 20160分钟 (2周)
- 实际时间 = 最近2016个区块的实际生成时间

限制:
- 难度变化不超过4倍（防止剧烈波动）
- 最小难度有下限
```

**示例:**

```
情况1: 算力增加，出块变快
- 期望时间: 20160分钟
- 实际时间: 10080分钟 (1周，快了一倍)
- 新难度 = 旧难度 × (10080 / 20160) = 旧难度 × 0.5

等等，公式反了！应该是:
- 新难度 = 旧难度 × (实际时间 / 期望时间)
- 新难度 = 旧难度 × (10080 / 20160) = 旧难度 × 0.5

不对，让我重新思考...

实际上应该是:
新难度 = 旧难度 × (期望时间 / 实际时间)

情况1: 出块太快（算力增加）
- 实际时间: 10080分钟 (1周)
- 新难度 = 旧难度 × (20160 / 10080) = 旧难度 × 2
- 难度增加，出块变慢

情况2: 出块太慢（算力减少）
- 实际时间: 40320分钟 (4周)
- 新难度 = 旧难度 × (20160 / 40320) = 旧难度 × 0.5
- 难度降低，出块变快
```

#### 2.2.4、PoW的优势与劣势

**优势:**

| 优势 | 说明 |
|------|------|
| **安全性高** | 51%攻击成本极高，需要控制全网51%算力 |
| **完全去中心化** | 任何人都可以参与挖矿 |
| **经过验证** | 比特币运行15年，证明了其可靠性 |
| **抗女巫攻击** | 通过工作量而非身份控制网络 |
| **公平性** | 算力贡献决定收益，无需许可 |

**劣势:**

| 劣势 | 说明 |
|------|------|
| **能耗巨大** | 比特币网络年耗电量超过一些国家 |
| **扩展性差** | 比特币TPS仅约7笔，以太坊约15笔 |
| **确认时间长** | 比特币需要约60分钟（6个确认） |
| **算力中心化** | 大型矿池控制大部分算力 |
| **资源浪费** | 计算不产生实际价值，只为了共识 |

**51%攻击分析:**

假设攻击者想要控制比特币网络：

```
当前比特币全网算力: ~400 EH/s (exahashes per second)
需要控制的算力: >200 EH/s

成本估算:
1. 硬件成本:
   - 最先进矿机: Antminer S19 Pro (110 TH/s)
   - 需要数量: 200,000,000 TH/s ÷ 110 TH/s ≈ 1,818,182台
   - 单价: ~$5,000
   - 总成本: 超过90亿美元

2. 电力成本:
   - 功耗: ~3000W/台
   - 总功耗: ~5.5 GW
   - 月电费: 数千万美元

3. 其他成本:
   - 场地、冷却、维护...

而且即使攻击成功，比特币价格会暴跌，攻击者的收益远小于成本。
```

### 2.3、权益证明 (Proof of Stake, PoS)

PoS是为了解决PoW高能耗问题而提出的替代方案。以太坊2.0已经从PoW转向PoS。

#### 2.3.1、PoS的核心思想

**基本原理:**

不再通过算力竞争，而是根据**持币数量和时间**来分配记账权。

```
获得记账权的概率 ∝ 质押的代币数量 × 质押时间

核心逻辑:
- 持币越多，对网络的"stake"(权益)越大
- 攻击网络会导致自己持有的币贬值
- 因此持币者有动机维护网络安全
```

**与PoW的本质区别:**

| 维度 | PoW | PoS |
|------|-----|-----|
| **资源投入** | 算力（外部资源） | 代币（内部资源） |
| **能耗** | 高 | 低 |
| **硬件要求** | 专业矿机 | 普通计算机 |
| **准入门槛** | 需要购买矿机 | 需要持有代币 |
| **攻击成本** | 购买51%算力 | 持有51%代币 |

#### 2.3.2、PoS的工作流程

以以太坊2.0为例：

**1. 成为验证者**

```
条件:
- 质押32 ETH
- 运行验证者节点
- 保持在线（如果离线会被惩罚）

质押过程:
1. 将32 ETH存入质押合约
2. 生成验证者密钥对
3. 注册成为验证者
4. 等待激活
```

**2. 验证者选择**

每个epoch（约6.4分钟），网络会：

```
1. 随机选择验证者
   - 使用VRF(可验证随机函数)
   - 考虑质押金额和质押时间
   - 无法预测或操纵

2. 分配任务
   - 提议者(Proposer): 提议新区块
   - 证明者(Attesters): 投票证明区块有效性
```

**3. 区块生成和确认**

```
Slot时间(12秒):
  
  1. 提议者创建区块
     - 收集交易
     - 构建区块
     - 广播给网络

  2. 证明者投票
     - 验证区块有效性
     - 对区块进行投票(attestation)
     - 需要2/3的验证者同意

  3. 区块最终化
     - 区块被添加到链上
     - 成为最终确认状态
```

**4. 奖励和惩罚**

**奖励机制:**
```
验证者可以获得奖励:
- 成功提议区块: 提议奖励
- 及时投票: 投票奖励
- 参与最终化: 最终化奖励

奖励率: 约4-5% 年化收益
```

**惩罚机制(Slashing):**
```
以下行为会被削减质押:

1. 双签(Double Signing)
   - 在同一高度签署两个不同区块
   - 惩罚: 削减质押金的一部分

2. 环绕投票(Surround Voting)
   - 对冲突的检查点投票
   - 惩罚: 严重削减

3. 长期离线
   - 验证者长时间不参与
   - 惩罚: 逐渐减少质押金
```

#### 2.3.3、PoS的优势与挑战

**优势:**

1. **能效高**: 不需要大量计算，能耗降低99.95%
2. **更去中心化**: 降低了参与门槛，更多人可以成为验证者
3. **经济安全**: 攻击者需要持有大量代币，攻击成本高
4. **可惩罚**: 可以直接惩罚作恶者（削减质押）

**挑战:**

1. **Nothing at Stake问题**

在分叉时，验证者可能在所有分叉上都签名（因为没有成本）：

```
Chain A:  Block 100A
                \
                 ├─ 验证者同时在两条链上签名
                /
Chain B:  Block 100B

解决方案:
- Slashing机制: 双签会被惩罚
- 经济惩罚足够大，使得作恶成本大于收益
```

2. **长程攻击(Long Range Attack)**

攻击者可以从很早的历史分叉点创建新链：

```
主链:     Block 1 → ... → Block 1000 → Block 1001
                   \
攻击链:             \→ Block 1000' → Block 1001'

攻击者可能持有早期的私钥，在历史上拥有大量权益

解决方案:
- 弱主观性(Weak Subjectivity): 节点定期检查点
- 只接受最近检查点之后的分叉
```

3. **富者越富**

持币多的验证者获得更多奖励，可能导致中心化。

### 2.4、委托权益证明 (DPoS)

DPoS是PoS的一个变种，通过投票选举代表来提高效率。

#### 2.4.1、DPoS工作原理

**核心思想:**

```
持币者投票选举代表(Delegates/Witnesses)
↓
代表轮流生产区块
↓  
如果代表表现不佳，可以被投票替换
```

**与PoS的区别:**

| 特性 | PoS | DPoS |
|------|-----|------|
| **谁可以生产区块** | 所有质押者（随机选择） | 选举出的代表 |
| **验证者数量** | 数千到数万 | 通常21-101个 |
| **TPS** | 中等 | 高 |
| **去中心化程度** | 高 | 中等 |
| **确认时间** | 秒级 | 秒级或更快 |

#### 2.4.2、DPoS示例: EOS

EOS使用21个区块生产者(Block Producers, BPs):

```
选举机制:
1. 持币者投票（1 EOS = 1票，可以投给最多30个候选人）
2. 得票最多的21个候选人成为BPs
3. 每隔一段时间重新计票

区块生产:
1. 21个BPs轮流生产区块
2. 每个BP连续生产6个区块
3. 每0.5秒一个区块
4. 如果BP离线，跳过其轮次

激励机制:
- BPs获得区块奖励
- 候选BP（得票靠前但未进入前21）也获得部分奖励
- 如果BP作恶或离线，会被投票替换
```

**DPoS的优劣:**

**优势:**
- TPS高（EOS可达4000+ TPS）
- 确认快（秒级最终确认）
- 能耗低

**劣势:**
- 去中心化程度较低（只有21个节点）
- 存在贿选风险
- 可能形成"卡特尔"

### 2.5、实用拜占庭容错 (PBFT)

PBFT是一种经典的拜占庭容错算法，常用于联盟链。

#### 2.5.1、PBFT的基本原理

**核心思想:**

通过多轮投票达成共识，可以容忍最多 (n-1)/3 个拜占庭节点。

**适用场景:**
- 联盟链（节点数量有限且相对可信）
- 需要快速最终确认的场景
- 对性能要求高的企业应用

#### 2.5.2、PBFT三阶段协议

PBFT通过三个阶段达成共识：

```
客户端请求 → Pre-Prepare → Prepare → Commit → Reply
```

**详细流程:**

**阶段1: Pre-Prepare (预准备)**

```
1. 客户端发送请求给主节点(Primary)
   Request = <operation, timestamp, client_id>

2. 主节点广播Pre-Prepare消息
   Pre-Prepare = <v, n, d>
   其中:
   - v: 视图编号(view number)
   - n: 序列号(sequence number)
   - d: 请求摘要 digest = H(request)

3. 备份节点验证:
   - 签名正确
   - 视图编号正确
   - 序列号在水线内
   - 摘要匹配
```

**阶段2: Prepare (准备)**

```
1. 备份节点收到Pre-Prepare后，广播Prepare消息
   Prepare = <v, n, d, i>
   其中 i 是节点编号

2. 每个节点收集Prepare消息
   - 需要收到2f个匹配的Prepare（包括自己的）
   - f = (n-1)/3 是最大拜占庭节点数

3. 准备完成(Prepared)条件:
   - 收到Pre-Prepare
   - 收到2f个匹配的Prepare
   
   此时节点进入prepared状态
```

**阶段3: Commit (提交)**

```
1. 节点prepared后，广播Commit消息
   Commit = <v, n, d, i>

2. 每个节点收集Commit消息  
   - 需要收到2f+1个匹配的Commit（包括自己的）

3. 提交完成(Committed)条件:
   - 已经prepared
   - 收到2f+1个Commit
   
4. 执行请求并回复客户端
```

**为什么需要三个阶段？**

- **Pre-Prepare**: 确保请求在正确的序列号上
- **Prepare**: 确保诚实节点在同一序列号上达成一致
- **Commit**: 确保足够多的节点承诺执行这个请求

**视图切换(View Change):**

如果主节点故障或作恶，需要切换视图：

```
触发条件:
- 主节点超时未响应
- Pre-Prepare消息异常

切换流程:
1. 节点广播View-Change消息
2. 新主节点收集2f+1个View-Change
3. 广播New-View消息
4. 开始新视图的共识
```

#### 2.5.3、PBFT的优劣

**优势:**
- 最终确认快（3轮通信即可确定）
- 可以容忍拜占庭节点
- 不需要挖矿或质押

**劣势:**
- 通信复杂度O(n²)，不适合大规模网络
- 需要提前知道所有节点
- 节点动态加入/退出困难

### 2.6、共识机制对比总结

| 共识机制 | TPS | 确认时间 | 能耗 | 去中心化 | 容错 | 代表项目 |
|---------|-----|---------|------|---------|------|---------|
| **PoW** | 7-15 | 10-60分钟 | 极高 | 高 | 51% | Bitcoin |
| **PoS** | 100-1000 | 秒级 | 低 | 中-高 | 51% | Ethereum 2.0 |
| **DPoS** | 1000-10000 | 秒级 | 低 | 中 | 51% | EOS, Tron |
| **PBFT** | 1000-10000 | 秒级 | 低 | 低 | 33% | Hyperledger Fabric |

**选择建议:**

- **公链，高安全性要求**: PoW或PoS
- **公链，高性能要求**: DPoS
- **联盟链**: PBFT或其变种
- **私有链**: 简化的共识机制
