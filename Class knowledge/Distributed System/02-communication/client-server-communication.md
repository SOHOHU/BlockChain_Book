# 客户端服务器通信

## 📌 通信协议栈

分布式系统的通信建立在多层协议之上：

```
┌─────────────────────────────┐
│      应用层 Applications     │
├─────────────────────────────┤
│      中间件层 Middleware      │
│  - RMI/RPC                  │
│  - 请求-应答协议             │
│  - 编组/解组                 │
├─────────────────────────────┤
│    传输层 Transport Layer    │
│  - UDP / TCP                │
├─────────────────────────────┤
│    网络层 Network Layer      │
│  - IP                       │
├─────────────────────────────┤
│    数据链路层 Data Link      │
└─────────────────────────────┘
```

## 🔌 传输层协议：UDP vs TCP

### UDP（User Datagram Protocol）

**特点**：
- 无连接
- 不可靠
- 无序
- 轻量级

**数据报结构**：
```
┌─────────┬─────────┬─────────┬─────────┬──────────┐
│ 源端口  │ 目标端口 │ 长度    │ 校验和  │   数据   │
│ (16位)  │ (16位)  │ (16位)  │ (16位)  │          │
└─────────┴─────────┴─────────┴─────────┴──────────┘
```

**优点**：
- ✅ 低延迟
- ✅ 低开销
- ✅ 支持广播/组播

**缺点**：
- ❌ 可能丢包
- ❌ 可能乱序
- ❌ 无流量控制

**适用场景**：
- 视频/音频流
- DNS查询
- 实时游戏
- 传感器数据

### TCP（Transmission Control Protocol）

**特点**：
- 面向连接
- 可靠传输
- 有序传输
- 流量控制

**连接建立（三次握手）**：
```
客户端                        服务器
  │                             │
  │─────── SYN ───────────────>│
  │                             │
  │<────── SYN-ACK ────────────│
  │                             │
  │─────── ACK ───────────────>│
  │                             │
  │      连接建立完成            │
```

**数据传输**：
```
客户端                        服务器
  │                             │
  │─────── Data ──────────────>│
  │                             │
  │<────── ACK ────────────────│
  │                             │
  │─────── Data ──────────────>│
  │                             │
  │<────── ACK ────────────────│
```

**连接终止（四次挥手）**：
```
客户端                        服务器
  │                             │
  │─────── FIN ───────────────>│
  │                             │
  │<────── ACK ────────────────│
  │                             │
  │<────── FIN ────────────────│
  │                             │
  │─────── ACK ───────────────>│
  │                             │
  │      连接关闭完成            │
```

**优点**：
- ✅ 可靠传输
- ✅ 有序保证
- ✅ 流量控制
- ✅ 拥塞控制

**缺点**：
- ❌ 连接开销
- ❌ 较高延迟
- ❌ 不支持广播

**适用场景**：
- HTTP/HTTPS
- 文件传输
- 电子邮件
- 数据库连接

### UDP vs TCP 对比表

| 特性 | UDP | TCP |
|------|-----|-----|
| 连接 | 无连接 | 面向连接 |
| 可靠性 | 不可靠 | 可靠 |
| 有序性 | 无保证 | 保证有序 |
| 速度 | 快 | 较慢 |
| 开销 | 低 | 高 |
| 头部大小 | 8字节 | 20-60字节 |
| 流量控制 | 无 | 有 |
| 拥塞控制 | 无 | 有 |
| 应用场景 | 实时、可容忍丢失 | 要求可靠性 |

## 💬 请求-应答协议

### 基本模式

客户端-服务器交互的基本模式：

```
┌────────┐                      ┌────────┐
│ Client │                      │ Server │
└───┬────┘                      └───┬────┘
    │                               │
    │─────── Request ──────────────>│
    │                               │
    │      (服务器处理请求)          │
    │                               │
    │<────── Reply ─────────────────│
    │                               │
```

### 请求-应答协议设计

#### 消息格式

**请求消息**：
```
┌──────────┬──────────┬──────────┬──────────┐
│ 请求ID   │ 操作类型  │ 参数     │ 数据     │
│ (唯一标识)│          │          │          │
└──────────┴──────────┴──────────┴──────────┘
```

**应答消息**：
```
┌──────────┬──────────┬──────────┐
│ 请求ID   │ 状态码   │ 结果数据  │
│ (对应请求)│          │          │
└──────────┴──────────┴──────────┘
```

#### 请求ID的作用

1. **匹配请求和应答**
   ```
   客户端可能同时发送多个请求
   通过ID匹配对应的应答
   ```

2. **检测重复**
   ```
   服务器可以检测重复的请求
   避免重复执行
   ```

3. **支持异步**
   ```
   客户端不必按顺序等待应答
   可以并发处理多个请求
   ```

### 故障处理

#### 1. 超时和重传

**问题**：请求或应答可能在网络中丢失

**解决方案**：
```
客户端                        服务器
  │                             │
  │─────── Request(ID=1) ──────>│
  │                             │
  │      等待超时时间            │
  │                             │
  │ (超时，重传)                 │
  │─────── Request(ID=1) ──────>│
  │                             │
  │<────── Reply(ID=1) ─────────│
```

**实现**：
```python
def send_request(request, timeout=5, max_retries=3):
    for attempt in range(max_retries):
        send(request)
        reply = wait_for_reply(timeout)
        if reply is not None:
            return reply
        print(f"Timeout, retry {attempt + 1}")
    raise TimeoutError("Max retries exceeded")
```

#### 2. 幂等性（Idempotency）

**问题**：重传可能导致操作被执行多次

**幂等操作**：执行多次与执行一次效果相同
```
✅ 幂等操作:
   - 读取文件
   - 设置变量值: x = 10
   - 删除文件

❌ 非幂等操作:
   - 转账（会重复扣款）
   - 追加到文件
   - 计数器加1: x = x + 1
```

**解决方案**：
- 服务器记录已处理的请求ID
- 检测到重复请求时返回缓存的结果

```python
# 服务器端
processed_requests = {}

def handle_request(request):
    request_id = request.id
    
    # 检查是否已处理
    if request_id in processed_requests:
        return processed_requests[request_id]
    
    # 处理请求
    result = process(request)
    
    # 缓存结果
    processed_requests[request_id] = result
    
    return result
```

#### 3. 至少一次 vs 至多一次

**至少一次（At-least-once）**：
- 保证操作至少执行一次
- 可能执行多次
- 通过重传实现
- 适合幂等操作

**至多一次（At-most-once）**：
- 保证操作最多执行一次
- 可能不执行
- 需要去重机制
- 适合非幂等操作

**恰好一次（Exactly-once）**：
- 理想情况
- 在分布式系统中很难实现
- 通常通过事务机制实现

### 异步请求-应答

#### 同步模式

```
客户端                        服务器
  │                             │
  │─────── Request 1 ──────────>│
  │                             │
  │ (阻塞等待)                   │
  │                             │
  │<────── Reply 1 ─────────────│
  │                             │
  │─────── Request 2 ──────────>│
  │                             │
  │ (阻塞等待)                   │
  │                             │
  │<────── Reply 2 ─────────────│
```

**特点**：
- 简单直观
- 低效（串行处理）

#### 异步模式

```
客户端                        服务器
  │                             │
  │─────── Request 1 ──────────>│
  │                             │
  │─────── Request 2 ──────────>│
  │                             │
  │<────── Reply 2 ─────────────│
  │                             │
  │<────── Reply 1 ─────────────│
```

**特点**：
- 高效（并发处理）
- 复杂度较高
- 需要请求ID匹配

**实现示例**：
```python
import asyncio

async def async_request(request):
    send(request)
    reply = await wait_for_reply_async()
    return reply

# 并发发送多个请求
async def send_multiple():
    tasks = [
        async_request(request1),
        async_request(request2),
        async_request(request3)
    ]
    results = await asyncio.gather(*tasks)
    return results
```

## 🔄 HTTP请求-应答

HTTP是最广泛使用的请求-应答协议。

### HTTP方法

| 方法 | 幂等性 | 安全性 | 用途 |
|------|--------|--------|------|
| GET | ✅ | ✅ | 获取资源 |
| POST | ❌ | ❌ | 创建资源 |
| PUT | ✅ | ❌ | 更新资源 |
| DELETE | ✅ | ❌ | 删除资源 |
| HEAD | ✅ | ✅ | 获取元数据 |
| OPTIONS | ✅ | ✅ | 获取支持的方法 |
| PATCH | ❌ | ❌ | 部分更新 |

**幂等性说明**：
```
GET /user/123     # 多次调用结果相同 ✅
POST /user        # 多次调用创建多个用户 ❌
PUT /user/123     # 多次调用结果相同 ✅
DELETE /user/123  # 多次调用结果相同（用户仍然被删除）✅
```

### HTTP请求示例

```http
GET /api/users/123 HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0
Accept: application/json
Authorization: Bearer token123
```

### HTTP响应示例

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 85

{
  "id": 123,
  "name": "Alice",
  "email": "alice@example.com"
}
```

### HTTP状态码

| 类别 | 范围 | 含义 | 示例 |
|------|------|------|------|
| 1xx | 信息 | 请求已接收 | 100 Continue |
| 2xx | 成功 | 请求成功 | 200 OK, 201 Created |
| 3xx | 重定向 | 需要进一步操作 | 301 Moved, 304 Not Modified |
| 4xx | 客户端错误 | 请求有误 | 400 Bad Request, 404 Not Found |
| 5xx | 服务器错误 | 服务器失败 | 500 Internal Error, 503 Unavailable |

### RESTful API设计

**REST原则**：
1. **资源（Resources）**：URL标识资源
2. **表示（Representations）**：JSON/XML表示
3. **无状态（Stateless）**：每个请求独立
4. **统一接口（Uniform Interface）**：使用HTTP方法

**示例**：
```http
# 获取用户列表
GET /api/users

# 获取单个用户
GET /api/users/123

# 创建用户
POST /api/users
Body: {"name": "Bob", "email": "bob@example.com"}

# 更新用户
PUT /api/users/123
Body: {"name": "Bob Updated", "email": "bob@example.com"}

# 删除用户
DELETE /api/users/123
```

## 🔑 关键要点

1. **传输层**：UDP快但不可靠，TCP可靠但开销大
2. **请求-应答**：分布式通信的基本模式
3. **故障处理**：超时重传、幂等性、去重
4. **异步通信**：提高效率，支持并发
5. **HTTP**：最广泛的请求-应答协议实现
