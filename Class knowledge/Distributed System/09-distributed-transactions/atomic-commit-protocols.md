# 原子提交协议

## 📌 问题：为什么需要原子提交？

### 生活场景

```
场景：你和朋友约好一起去旅游

你：订机票 ✓
朋友1：订酒店 ✓  
朋友2：请假 ✗（老板不批准）

问题：朋友2请不了假，大家都去不了
但你已经订了机票，朋友1订了酒店
怎么办？

解决：要么都成功，要么都取消（原子性）
```

### 技术场景：银行转账

```
场景：小明给小红转账100元

需要两个操作：
操作1：小明账户-100元（银行A的服务器）
操作2：小红账户+100元（银行B的服务器）

可能出现的问题：
┌────────────────────────────────────────┐
│ 操作1成功：小明-100元 ✓                │
│ 网络故障！                              │
│ 操作2失败：小红没有+100元 ✗            │
│                                        │
│ 结果：100元消失了！                     │
└────────────────────────────────────────┘

必须保证：
- 要么两个操作都成功
- 要么两个操作都失败（回滚）
- 不能只成功一个！

这就需要原子提交协议！
```

## 🔄 两阶段提交（2PC）

**核心思想**：就像做决定前先征求所有人意见

### 角色

- **协调者（Coordinator）**：像组长，负责协调
- **参与者（Participant）**：像组员，执行具体操作

### 生活类比

```
场景：全家决定周末去哪里玩

协调者（爸爸）：我们周末去爬山，大家准备好了吗？

阶段1：询问是否准备好
爸爸 → 妈妈：你准备好了吗？
妈妈 → 爸爸：准备好了 ✓

爸爸 → 哥哥：你准备好了吗？
哥哥 → 爸爸：准备好了 ✓

爸爸 → 弟弟：你准备好了吗？
弟弟 → 爸爸：我作业没写完，去不了 ✗

阶段2：做出最终决定
因为弟弟去不了，所以：
爸爸 → 所有人：取消！大家都不去了

这就是两阶段提交！
```

### 流程详解

**阶段1：准备阶段（Prepare / Voting Phase）**

```
协调者的思路：
"我要提交事务了，但要先问问大家能不能提交"

步骤：
1. 协调者 → 所有参与者："准备提交事务，你们准备好了吗？"
2. 参与者收到请求后：
   - 检查能否完成操作
   - 准备好所需资源
   - 把数据写到临时区域（还没真正提交）
   - 回复"YES"或"NO"
3. 协调者等待所有参与者回复
```

**阶段2：提交/中止阶段（Commit / Abort Phase）**

```
协调者的决策：
- 如果所有参与者都说"YES" → 决定提交
- 如果任何一个参与者说"NO" → 决定中止

步骤：
1. 协调者根据投票结果做决定
2. 协调者 → 所有参与者："提交"或"中止"
3. 参与者执行最终操作：
   - 收到"提交"：真正写入数据
   - 收到"中止"：丢弃临时数据
4. 参与者回复"完成"
5. 协调者收到所有回复，事务结束
```

### 详细示例1：转账成功

```
场景：小明（账户在银行A）给小红（账户在银行B）转100元

角色：
- 协调者：转账系统
- 参与者A：银行A的数据库服务器
- 参与者B：银行B的数据库服务器

初始状态：
小明余额：1000元（银行A）
小红余额：500元（银行B）

━━━━━━━━━ 阶段1：准备阶段 ━━━━━━━━━

[时间 10:00:00]
协调者：好的，我要处理转账，先问大家能不能做

协调者 → 参与者A：
"请准备：小明账户-100元，能做到吗？"

[时间 10:00:01]
参与者A收到请求：
1. 检查小明余额：1000元 > 100元 ✓
2. 锁定小明账户（不让别人同时转账）
3. 在临时区域记录：小明余额将变为900元
4. 写入日志："准备扣除小明100元"
5. 还没真正扣钱！

参与者A → 协调者："YES，我准备好了"

[时间 10:00:02]
协调者 → 参与者B：
"请准备：小红账户+100元，能做到吗？"

[时间 10:00:03]
参与者B收到请求：
1. 锁定小红账户
2. 在临时区域记录：小红余额将变为600元
3. 写入日志："准备增加小红100元"
4. 还没真正加钱！

参与者B → 协调者："YES，我准备好了"

[时间 10:00:04]
协调者：
收到A和B的回复，都是YES
决定：提交事务！

━━━━━━━━━ 阶段2：提交阶段 ━━━━━━━━━

[时间 10:00:05]
协调者 → 参与者A："COMMIT（提交）"
协调者 → 参与者B："COMMIT（提交）"

[时间 10:00:06]
参与者A：
1. 真正执行：小明余额 1000 - 100 = 900元
2. 写入数据库
3. 释放锁
4. 写日志："已提交"

参与者A → 协调者："已完成提交"

[时间 10:00:07]
参与者B：
1. 真正执行：小红余额 500 + 100 = 600元
2. 写入数据库
3. 释放锁
4. 写日志："已提交"

参与者B → 协调者："已完成提交"

[时间 10:00:08]
协调者：所有参与者都完成了，事务成功！

最终状态：
小明余额：900元 ✓
小红余额：600元 ✓
转账成功！💰
```

### 详细示例2：转账失败（余额不足）

```
场景：小刚（账户在银行C）给小丽（账户在银行D）转1000元
但是小刚只有500元！

初始状态：
小刚余额：500元（银行C）
小丽余额：300元（银行D）

━━━━━━━━━ 阶段1：准备阶段 ━━━━━━━━━

[时间 11:00:00]
协调者 → 参与者C：
"请准备：小刚账户-1000元"

[时间 11:00:01]
参与者C收到请求：
1. 检查小刚余额：500元 < 1000元 ✗
2. 余额不足！无法完成操作

参与者C → 协调者："NO，余额不足"

[时间 11:00:02]
协调者 → 参与者D：
"请准备：小丽账户+1000元"

[时间 11:00:03]
参与者D收到请求：
1. 锁定小丽账户
2. 准备好增加1000元

参与者D → 协调者："YES，我准备好了"

[时间 11:00:04]
协调者：
收到C的NO，收到D的YES
只要有一个NO，就必须中止！
决定：中止事务！

━━━━━━━━━ 阶段2：中止阶段 ━━━━━━━━━

[时间 11:00:05]
协调者 → 参与者C："ABORT（中止）"
协调者 → 参与者D："ABORT（中止）"

[时间 11:00:06]
参与者C：
1. 什么都不做（本来就没法执行）
2. 写日志："已中止"

参与者C → 协调者："已中止"

[时间 11:00:07]
参与者D：
1. 丢弃临时数据
2. 释放锁
3. 恢复原状态
4. 写日志："已中止"

参与者D → 协调者："已中止"

最终状态：
小刚余额：500元（未变）
小丽余额：300元（未变）
转账失败，但数据一致！✓
```

### 为什么需要两个阶段？

```
如果只有一个阶段会怎样？

❌ 错误的单阶段做法：
协调者 → 参与者A："扣钱"
参与者A：执行成功 ✓
协调者 → 参与者B："加钱"
参与者B：执行失败 ✗（比如服务器崩溃）

结果：钱扣了但没加上 → 钱丢了！

✓ 两阶段的好处：
阶段1：先问大家"能做到吗？"
  - 如果有人做不到，还没开始改数据
  - 可以安全地取消
  
阶段2：所有人都说能做到后，再真正执行
  - 保证要么都成功，要么都失败
```

### 故障处理

**参与者故障**：
```
阶段1：参与者无响应→协调者中止事务
阶段2：参与者重启后读日志恢复
```

**协调者故障**：
```
问题：参与者不知道最终决定
解决：协调者恢复后根据日志重新发送决定
```

### 缺点

**阻塞问题**：
```
阶段1后，参与者进入准备状态
如果协调者崩溃→参与者阻塞等待
无法单方面提交或中止
```

## 🔄 三阶段提交（3PC）

### 目标

解决2PC的阻塞问题

### 流程

**阶段1：CanCommit**
```
协调者询问参与者是否可以提交
```

**阶段2：PreCommit**
```
所有参与者同意→发送预提交
参与者准备但不提交
```

**阶段3：DoCommit**
```
最终提交决定
```

### 优点

- ✅ 减少阻塞（超时可以决定）
- ✅ 增加中间状态

### 缺点

- ❌ 更复杂
- ❌ 网络分区仍有问题

## 🔑 关键要点

1. **2PC**：两阶段提交，简单但会阻塞
2. **3PC**：三阶段提交，减少阻塞
3. **权衡**：一致性 vs 可用性
