

# Kaia 是“以太坊兼容 + 高性能 + 亚洲生态导向”的链

| 项目 | 以太坊                | Kaia                                       |
| -- | ------------------ | ------------------------------------------ |
| 定位 | 全球最成熟的 L1 区块链，生态最大 | 亚洲导向的高性能 L1，EVM 完全兼容                       |
| 起源 | 独立发展               | 由 Klaytn（韩国 Kakao 支持）与 Finschia（LINE 支持）合并 |
| 目标 | 去中心化、全球性           | 重点在企业级应用、Web3 大众化、亚洲市场                     |

---

# 从用户角度的区别（性能、费用、钱包体验）

| 特性            | 以太坊               | Kaia                                                       | 开发者影响             |
| ------------- | ----------------- | ---------------------------------------------------------- | ----------------- |
| TPS（每秒交易量）    | 15–30 TPS         | 高达 4,000 TPS                                               | 高并发应用（游戏、支付）运行更流畅 |
| 区块生成时间        | ~12 秒             | 1 秒                                                        | 用户几乎“即时”看到结果      |
| 终局性（Finality） | 约 13–15 分钟（概率终局）  | 即时终局（PBFT / IBFT 类共识）                                      | 无需等待多次确认          |
| 手续费（Gas）      | 浮动，EIP-1559 模型    | 同样兼容 EIP-1559 思路，但配置与实现有差异；支持 Fee Delegation、Key 相关 Gas 计费 | 用户体验更好，可由应用方代付    |
| 钱包            | MetaMask、Ledger 等 | 完全兼容 + Kaia Wallet                                         | 几乎不需要改钱包配置        |

**补充说明（用户角度）**

* Kaia 的 1 秒区块 + BFT 样式最终性意味着用户看到交易成功后几乎即可认为交易“确定”，这在支付、游戏、点对点即时服务场景中非常重要。
* Kaia 对费用体验的优化（更细化的 gas 项、原生费用代付）大幅降低了对用户预付 gas 的门槛，能更容易实现“免 gas 上手”的产品体验（类似 Web2 的免费 UX）。

# 从开发者角度的区别（EVM 兼容性、交易结构、账户模型）

| 特性      | 以太坊                   | Kaia                                     |
| ------- | --------------------- | ---------------------------------------- |
| 虚拟机     | EVM                   | KVM（Kaia Virtual Machine）——兼容 EVM，但带原生扩展 |
| 智能合约语言  | Solidity、Vyper、Yul    | 一样支持（Solidity 等）                         |
| 开发工具    | Remix、Hardhat、Foundry | 全兼容，还提供 Kaia SDK                         |
| Web3 库  | ethers.js、web3.js 等   | 同样支持 + “ext” 扩展版本                        |
| 交易类型    | Legacy、EIP-1559 等     | 支持全部 + 额外的费用委托与分摊交易类型                    |
| 账户模型    | 仅 EOA + 合约账户          | 内建账户抽象（多密钥、角色分级、可替换密钥）                   |
| RPC API | `eth_` 命名空间           | 同样支持 + `kaia_` 命名空间用于特有功能                |

---

### 1. **EVM 兼容性（KVM）**

* KVM 保持对 EVM 操作码的兼容，Solidity 合约在语法和大多数运行时语义上与以太坊一致，因此迁移成本低。
* 但 Kaia 在协议层增加了**额外的预编译合约与不同的地址范围**（用于扩展功能：例如专用验证、费用相关原语、zk/BLS 支持等），所以依赖特定预编译地址或行为的合约需要检查并适配。
* 开发工具（Remix/Hardhat/Foundry）可直接使用，通常只需修改 RPC endpoint 与 chainId 即可部署。

### 2. **额外交易类型（协议级）**

* Kaia 原生支持多种交易类型，常见并具有代表性的包括：

  * **Fee Delegation（费用委托）**：允许第三方（dApp、relayer）为交易支付 gas；交易在链上需要相应的双重签名或验证。
  * **Partial Fee Delegation（部分费用委托 / feeRatio）**：费用可以按比例分摊在多个付费方。
* 这些是协议级别的交易类型（不是只靠合约模拟），因此在 UX 与安全性上比纯合约方案更标准化与高效。

### 3. **账户抽象（Account Abstraction）与多密钥**

* Kaia 把账户抽象（address 与密钥解耦、多密钥/角色密钥）内置到账户模型：

  * 一个地址可以关联多个公钥（Owner、FeePayer、Recovery、RoleKey 等），并配置验证逻辑（阈值、多签权重）。
  * 允许在密钥泄露时替换账户密钥而不必迁移资产（减少运维和用户迁移成本）。
  * 原生支持社交恢复、分层权限与细粒度访问控制（本质上在协议层实现了一些 EIP-4337 的目标）。
* 对开发者而言，这意味着：

  * 钱包/后端需要考虑不同角色的签名流程；
  * 合约不必再做大量“多签合约”逻辑（除非合约本身需要）；
  * UX 可以更接近 Web2（例如用邮件/社交恢复替代私钥保管）。

### 4. **RPC 与 SDK 扩展**

* Kaia 保留 `eth_` 系列 RPC（保证兼容），同时提供 `kaia_` 系列扩展 RPC 用于访问协议特有能力（如费用委托、账户管理接口等）。
* 官方/社区 SDK（例如 `ethers-ext`、`web3js-ext` 或 Kaia SDK）提供一行式封装：构造代付交易、发起账户更新、管理多密钥等，不需手工拼装复杂的签名流程。

# 额外技术细节（Gas、预编译、交易费用机制）

### Gas 与费用计量的差异

* Kaia 在 gas 设计上除了支持 EIP-1559 风格的 baseFee/priorityFee 模型外，还更细化了与“账户/密钥”相关的费用项，例如：**KeyCreationGas、KeyValidationGas** 等，把帐户抽象的成本显式化计入 gas。
* Kaia 在不同发展阶段（不同 KIP/硬分叉）对 baseFee、tip、FCFS（先到先服务）策略、优先级费用等做过调整，其目标是：在保持可预测性的同时降低小额交易成本与阻止垃圾交易。
* 对 dApp 开发者与合约迁移者建议：在迁移时应通过测试网（或本地模拟）重新估算 gas，注意新增的 Key 相关 gas 项与预编译差异会影响 gasUsed。

### 预编译合约（Precompiles）

* Kaia 保留 EVM 常见预编译（如椭圆曲线、哈希等），同时新增/调整了若干预编译地址以支持 Kaia 特有功能（例如费用委托校验、链上账户管理原语、zk/BLS/KZG 支持等）。
* 如果合约或库依赖某些硬编码预编译地址（或假设预编译行为完全一致），迁移时需检查并替换相应地址/调用方式。

# ⚙️ 四、共识机制、节点架构与治理的不同

| 特性   | 以太坊                             | Kaia                                          |
| ---- | ------------------------------- | --------------------------------------------- |
| 共识算法 | Gasper（PoS: Casper + LMD-GHOST） | 优化版 IBFT / PBFT 变体                            |
| 节点架构 | Execution + Consensus 客户端       | 多层节点（CN 共识节点、PN 验证节点、EN 执行节点、Service Chain 等） |
| 治理   | 链下社区主导（EIP 提案）                  | 链上治理 + 治理委员会（GC）                              |
| 代币   | ETH                             | KAIA                                          |

**补充说明（共识与架构）**

* Kaia 倾向 BFT 风格（IBFT/PBFT 变体），带来**确定性最终性**、更短的确认延迟和更高吞吐。适合企业级应用与需要强最终性的场景。
* 节点分层（CN/PN/EN/Service Chain）使得网络可横向扩展和职责分离（如把某些服务或逻辑放到 service chains 上），更利于亚洲多租户、企业接入场景。
* 治理上 Kaia 更强调链上治理与治理委员会（更集中化的治理元素），这有利于快速迭代与企业合作，但相对以太坊社区治理模式会更偏向项目驱动。
