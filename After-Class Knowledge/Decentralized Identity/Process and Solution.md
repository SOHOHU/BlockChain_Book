### 1. ZKP对于DID的改进

---

去中心化身份（DID）相比传统的身份凭证系统，其革命性优势主要体现在对 **零知识证明（ZKP）** 的应用上，实现了对隐私保护的极致追求，即 **最小信息披露原则**。

在传统的身份验证中，如大学签发的数字证书，用户必须将证书中的**所有信息**（姓名、邮箱、完整学号等）提交给商家进行验证。这种模式是**全量披露**，极大地牺牲了用户隐私。

DID 的工作流程则彻底颠覆了这一点。它允许用户在本地利用 ZKP，将原始的完整证书作为**私有数据**（或称 **Witness**），只针对**验证方需要确认的特定命题**（或称 **Statement**）生成一个加密证明。

例如，用户只需向打折网站证明：“我的出生年份早于 2007 年”，而网站收到的只是一个简洁的 **ZK 证明**。网站运行验证程序后，只知道这个**命题成立**），但无法获取用户的具体生日、姓名或完整的证书内容。这种机制确保了对个人数据的 **最小化信息披露**，实现了隐私与信任的平衡。

另外一个问题是，传统的凭证一旦泄露，验证方可以追踪该凭证在所有场景下的使用记录。更复杂的是，如果一个证书需要被**撤销**（例如学生毕业），系统必须依赖一个**中心化的撤销列表**，且难以在不损害用户隐私的前提下验证其状态。

DID 利用 ZKP 解决了这一核心矛盾，实现了**可撤销性与匿名性的统一**：

发证方（例如大学）会周期性地将所有**有效**或**未被撤销**的证书 ID 聚合到一个加密数据结构中，例如 **Merkle Tree**，并将这个集合的根哈希（**Merkle Root**）发布到公共区块链上。这个 **Merkle Root** 成为了**公开且可验证的有效性证明**。

用户在验证时，不需要提交证书本身，而是生成一个 **ZK 证明**。这个证明断言：“我持有的证书 ID 存在于当前链上发布的那个 $\text{Merkle Root}$ 所代表的集合中”

验证方可以轻松通过验证，然后对证明者赋予某些权利。

### 2. 预言机对于DID的改进

---

下面我们需要考虑第二个问题：身份引导（Bootstrapping）

去中心化身份（DID）要实现其价值，必须解决一个巨大的工程难题：如何可信、安全地将用户在传统世界中积累的信任和权威证明——例如**政府签发的驾照、银行的 $\text{KYC}$ 记录**——引入到匿名的区块链世界中。这个过程被称为 **身份引导（Bootstrapping Identity）**，也是实现 $\text{CanDID}$ 架构的关键目标之一。

**去中心化预言机（Decentralized Oracles）**就是解决这个问题的方法。在这里，预言机不再是简单地传递资产价格，而是验证并证明用户提交的**链下身份凭证**的真实性。

（我们在Oracle中已经详细解释过预言机的基本原理，这里不再详细赘述，我们只强调预言机是如何实现DID的身份引导的）

* **安全连接与数据获取：** 用户首先通过安全的 **TLS 连接**（即我们日常使用的 $\text{HTTPS}$ 协议）访问传统的权威数据源（例如银行网站）。用户可以安全地获取一个由银行签署的身份证明文件。
* **提交至多节点：** 用户随后将这个经过 $\text{TLS}$ 认证的身份证明文件，提交给 $\text{DID}$ 网络中的**多个**独立的**去中心化节点**（图：屏幕截图 2025-10-06 151303.jpg）。
* **共识验证：** 这些节点充当**去中心化的验证者**，它们**共同协作**、独立验证用户提交的数据的真实性。这种多节点验证机制是至关重要的，因为它避免了**单点作恶**的风险。如果只有一个节点验证，一旦该节点被攻击或被收买，整个系统的信任基础就会崩溃。
* **DID 签发与链上锚定：** 在确认原始身份数据真实有效后，这些节点通过**门限签名（Threshold Signature）**等加密技术，联合签署一个证明。这个联合签署的证明随后被用于为用户**签发**一个基于区块链的**去中心化身份凭证**，最终生成 $\text{DID}$ 并记录到链上或分布式账本中。

### 3. DID 标识符的唯一性确认

---

解决完隐私和身份引导问题后，我们接下来需要考虑的是唯一性的问题。这要求 DID 必须具备强大的标识符结构。事实上，DID 标识符被设计成一种包含**加密逻辑**的复杂结构

一个成熟的 DID 标识符通常包含或指向以下三个关键的加密要素：

* **指纹与不可篡改性（哈希值）**：标识符中会包含或引用**身份文档的哈希值**。这个哈希值就像文件的 DNA，是文档内容的唯一指纹。它的存在保证了 DID 背后所关联的身份元数据（例如公钥列表、服务端点等）是**不可篡改**的，只要哈希值不变，文档内容就未曾被修改。
* **所有权与控制权（公钥）**：这是 DID 的核心所在。标识符中必须包含或指向一个**公钥**。只有持有相应**私钥**的用户，才会被系统确认为该 DID 的**唯一所有者**。这个公钥赋予了用户**控制权**，用于对 DID 文档进行更新、签署凭证或执行身份恢复。
* **使用策略与可编程性（程序逻辑）**：为了实现**最小权限（Least Authority）**原则，高级的 DID 标识符可以包含一段**程序逻辑**或**策略定义**。这段逻辑可以限定该 DID 允许进行的操作，例如规定“此 DID 仅用于 $\text{DAO}$ 投票，禁止用于高价值的金融交易”。

这个部分似乎难以理解， 我们用一个详细的例子加以阐释。

想象 Alice 想要创建一个 DID，专门用于去中心化自治组织（$\text{DAO}$）的投票，并且她希望这个身份不能被滥用作借贷抵押。

1. **创建与构成：** Alice 在钱包中生成一对密钥（公钥 $\text{PK}_{\text{Alice}}$ 和私钥 $\text{SK}_{\text{Alice}}$）。她的 DID 标识符最终被设计为：
    
    * **公钥锚定：** 标识符指向 $\text{PK}_{\text{Alice}}$，确立 Alice 的所有权。
    * **策略锁定：** 标识符关联的文档中明确写入**程序逻辑**：“此 $\text{DID}$ 的所有签名必须带有 $\text{purpose: voting}$ 标签”。
    * **哈希指纹：** 对整个 $\text{DID}$ 文档（包含公钥和策略）进行哈希，将哈希值作为 $\text{DID}$ 的指纹。
2. **首次使用（投票）：** Alice 参与 $\text{DAO}$ 投票时，她使用她的私钥 $\text{SK}_{\text{Alice}}$ 对投票交易进行签名。验证合约会检查：
    
    * 签名是否与 $\text{DID}$ 中记录的公钥 $\text{PK}_{\text{Alice}}$ 匹配（**所有权验证**）。
    * 签名是否符合**程序策略**（即是否包含 $\text{voting}$ 标签）。
    * 由于签名有效且符合策略，投票成功。
3. **防止滥用（借贷尝试）：** Alice 尝试使用这个 $\text{DID}$ 去一个借贷协议签署抵押交易。
    
    * 借贷协议的合约检查 $\text{DID}$ 的策略，发现其限制为 $\text{vote-only}$。
    * **结果：** 交易被拒绝。

这种方式在许多情况下可以确定一人一账户，有广泛的使用场景。

### 4. 密钥管理与账户的“社会恢复

在去中心化身份（DID）的世界中，用户对身份拥有完全的控制权，这权力集中在他们的**私钥**上。然而，这种权力带来了一个极大的风险：**私钥的丢失就意味着身份和所有资产的永久丢失**。为了避免这种灾难性的结果，同时又不引入任何中心化的第三方，DID 体系引入了**社会恢复（Social Recovery）**机制。

**社会恢复**机制的核心在于将身份的最终控制权分散给用户的**信任网络**。

它主要分为以下几个要点：

* **设定守护者：** 用户在创建 DID 或设置钱包时，会预先指定一组**“守护者（Guardians）”**。这些守护者通常是用户信任的朋友、家人、律师，也可以是用户拥有的其他安全设备（例如硬件钱包）。
* **启用恢复：** 当用户丢失了主私钥、无法登录其 DID 时，便可以启动恢复流程。
* **多数投票恢复：** 恢复流程要求**多数**预设的守护者（例如，如果设置了 5 个守护者，则需要其中 3 个签名同意）通过他们的私钥或身份，来**授权**恢复操作。
* **重置控制密钥：** 一旦达到门限数量的守护者同意，系统就会允许用户**重置**其 DID 的主控制密钥。用户随后设置一个新的主私钥，重新获得对其身份的完全控制权。

目前在许多DID模型中，守护者被设置为了预言机。
