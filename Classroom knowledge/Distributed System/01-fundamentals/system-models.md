# 系统模型

## 📌 什么是模型？

**模型（Model）**是一种抽象的、简化但一致的描述。

### 经典示例：冯·诺依曼计算机模型

冯·诺依曼模型定义了计算机的基本组成：
- CPU（中央处理器）
- 内存
- 输入/输出设备
- 它们之间的连接关系

## 🏗️ 模型的层次

### 1. 架构模型（Architectural Models）

**目的**：识别组件、描述功能、组件布局以及组件之间的关系

**关注点**：
- 系统由哪些组件构成？
- 各组件的功能是什么？
- 组件如何放置？
- 组件之间如何交互？

### 2. 基础模型（Fundamental Models）

**目的**：更形式化地描述架构模型中的共同和内在属性

**关注点**：
- 正确性（Correctness）
- 可靠性（Reliability）
- 安全性（Security）

**方法**：通过逻辑分析和数学证明来验证系统属性

## 🏛️ 架构模型

### 1. 软件与硬件层次（垂直视角）

```
┌─────────────────────────────┐
│     应用层 (Applications)    │
├─────────────────────────────┤
│   中间件层 (Middleware)      │
│   - 分布式对象/RMI           │
│   - 请求-应答协议            │
│   - 外部数据表示/编组        │
├─────────────────────────────┤
│   操作系统层 (OS)            │
│   - TCP/UDP                 │
│   - IP                      │
├─────────────────────────────┤
│   硬件层 (Hardware)          │
│   - 网络接口                │
│   - 计算机/设备             │
└─────────────────────────────┘
```

**中间件（Middleware）**：
- 位于操作系统和应用程序之间
- 提供高级编程抽象
- 掩盖底层网络、硬件、操作系统的异构性
- 提供统一的编程模型

### 2. 系统架构模式（水平视角）

#### 2.1 客户端-服务器模型（Client-Server）

**特点**：
- **服务器（Server）**：管理资源，提供服务
- **客户端（Client）**：请求服务
- 清晰的角色划分

**结构**：
```
         请求
Client ────────> Server
       <────────
         响应
```

**示例**：Web服务

```
┌──────────┐                  ┌──────────────┐
│ 浏览器    │ HTTP请求         │ Web服务器     │
│ (Client) │ ──────────────> │ (Server)     │
│          │ <────────────── │              │
│          │   HTML响应       │ 文件系统     │
└──────────┘                  └──────────────┘
```

**优点**：
- ✅ 集中式管理
- ✅ 易于维护
- ✅ 易于保障安全

**缺点**：
- ⚠️ 单点故障
- ⚠️ 性能瓶颈
- ⚠️ 可扩展性受限

#### 2.2 对等模型（Peer-to-Peer, P2P）

**特点**：
- 所有节点地位平等
- 每个节点既可以是客户端，也可以是服务器
- 去中心化架构

**结构**：
```
    Peer A ←──────→ Peer B
      ↕              ↕
    Peer C ←──────→ Peer D
```

**示例**：
- BitTorrent（文件共享）
- Skype（早期版本，P2P通话）
- 区块链网络

**优点**：
- ✅ 高度可扩展
- ✅ 无单点故障
- ✅ 资源共享高效

**缺点**：
- ⚠️ 管理复杂
- ⚠️ 安全性挑战
- ⚠️ 一致性难保证

#### 2.3 多层架构（Multi-tier Architecture）

**三层架构示例**：

```
┌─────────────────┐
│  表示层          │ ← 用户界面
│ (Presentation)  │
└────────┬────────┘
         │
┌────────▼────────┐
│  应用逻辑层      │ ← 业务逻辑
│ (Application)   │
└────────┬────────┘
         │
┌────────▼────────┐
│  数据层          │ ← 数据存储
│ (Data)          │
└─────────────────┘
```

**Web应用示例**：
- **表示层**：浏览器（HTML/CSS/JavaScript）
- **应用逻辑层**：Web服务器（业务逻辑处理）
- **数据层**：数据库服务器（数据持久化）

## 🔬 基础模型

### 1. 交互模型（Interaction Model）

**关注**：时间假设和行为

#### 1.1 同步分布式系统（Synchronous DS）

**假设**：
- ⏰ **进程执行时间有界**：每个进程步骤的执行时间有已知上界
- ⏰ **消息传输延迟有界**：消息传输时间有已知上界
- ⏰ **时钟漂移率有界**：本地时钟与全局参考时钟的差异有已知上界

**特点**：
- 可以使用超时来检测故障
- 能够实现时间相关的算法

**示例场景**：硬实时系统

#### 1.2 异步分布式系统（Asynchronous DS）

**假设**：
- ⏰ **进程执行时间无界**：没有时间上界
- ⏰ **消息传输延迟无界**：消息可能延迟任意长时间
- ⏰ **时钟漂移率无界**：时钟同步不保证

**特点**：
- 无法使用超时来可靠检测故障
- 更接近实际互联网环境
- 算法设计更具挑战性

**示例场景**：互联网应用

**实践中的处理**：
```
大多数实际系统介于两者之间
- 假设异步模型设计算法
- 使用超时作为启发式方法（不保证绝对正确）
```

### 2. 故障模型（Failure Model）

定义系统可能发生的故障类型。

#### 2.1 进程故障

| 故障类型 | 描述 | 示例 |
|---------|------|------|
| **遗漏故障** (Omission) | 进程崩溃，停止执行 | 服务器宕机 |
| **任意故障** (Arbitrary/Byzantine) | 进程表现出任意错误行为 | 发送错误数据、返回错误结果 |

#### 2.2 通信故障

| 故障类型 | 描述 | 示例 |
|---------|------|------|
| **发送遗漏** | 消息放入发送缓冲区后丢失 | 网络接口故障 |
| **接收遗漏** | 消息到达接收缓冲区但未被进程接收 | 接收缓冲区溢出 |
| **通道遗漏** | 消息在网络传输中丢失 | 网络拥塞、路由器故障 |
| **任意故障** | 消息被损坏、重复或伪造 | 恶意攻击 |

#### 故障严重程度（从轻到重）

```
遗漏故障 < 时序故障 < 任意故障（拜占庭）
   ↑                        ↑
容易处理                  最难处理
```

**拜占庭故障（Byzantine Failure）**：
- 不仅仅是失败，还会制造更多麻烦
- 可能任意省略处理步骤或执行非预期步骤
- **示例**：
  - 进程可能设置错误的数据值
  - 进程可能返回错误的结果
  - 消息可能被损坏、重复发送

### 3. 安全模型（Security Model）

关注系统中的安全威胁和防护机制（在安全相关章节详细讨论）。

## 🎯 模型的重要性

1. **抽象化**：简化复杂系统的理解
2. **设计指导**：为系统设计提供框架
3. **分析工具**：支持形式化验证和推理
4. **通信语言**：为开发者提供共同语言

## 🔑 关键要点

1. **架构模型**：
   - Client-Server：中心化，易管理但有单点故障
   - P2P：去中心化，可扩展但管理复杂
   
2. **交互模型**：
   - 同步系统：有时间界限，可用超时
   - 异步系统：无时间界限，更现实

3. **故障模型**：
   - 遗漏故障相对容易处理
   - 拜占庭故障最难处理
